# Backend — расчёт заказов поставщикам

Python 3.12 · FastAPI · SQLAlchemy + SQLite · pandas/numpy.
API реализует контракт из [`FRONTEND_TZ.md` §0.3–0.4](../FRONTEND_TZ.md).

База проекта — SQLite: `DATABASE_URL=sqlite:///./var/hackalem.db`.
При запуске из `backend/` данные хранятся в `backend/var/hackalem.db`.
Каталог и таблицы создаются при инициализации; отдельный сервер БД не требуется.
Для файловой базы включён режим WAL.

## Запуск

```bash
# один раз: uv (https://docs.astral.sh/uv/) сам поставит Python 3.12 и зависимости
cd backend
cp .env.example .env          # DATA_DIR — папка с xlsx партнёра (подпапки IEK и Systeme electric)
uv sync

uv run hackalem ingest        # xlsx → БД (~40 с), перезаливает данные поставщиков
uv run hackalem calc          # расчёт рекомендаций (~3 с)
uv run hackalem serve --reload  # API на http://127.0.0.1:8000, Swagger: /docs

uv run pytest                 # тесты (синтетические данные, реальные файлы не нужны)
uv run ruff check src tests
```

Фронт: `VITE_USE_MOCK=false`, `VITE_API_BASE_URL=http://127.0.0.1:8000/api` (CORS для `localhost:5173` открыт).

## Структура

```
src/app/
  main.py            FastAPI, CORS, роутеры, отдача файлов экспорта
  cli.py             hackalem ingest | calc | serve
  models.py          ORM-таблицы (ARCHITECTURE.md §3.1)
  schemas.py         Pydantic — 1:1 с TS-типами фронта
  etl/               адаптеры поставщиков → единая схема (SupplierBundle)
    iek.py, systeme.py, common.py, loader.py
  engine/            расчёт: чистые функции над DataFrame, без БД
    core.py          пайплайн
    explain.py       текстовые обоснования
  services/          прогон расчёта (calc_runs.py), экспорт для 1С (exporter.py)

```

Новый поставщик = новый модуль в `etl/` + строка в `ADAPTERS` (`etl/loader.py`).

## Методология расчёта (`engine/core.py`)

Всё считается по каждому SKU, дата расчёта — самая свежая дата в данных (последняя отгрузка / снимок остатков).

1. **Исключение разовых/оптовых заказов.** Для строк отгрузок SKU считаются медиана и MAD. Строка исключается,
   если одновременно: (а) `qty > max(median + k·σ̂, p95)`, σ̂ = max(1.4826·MAD, 0.5·median, 1);
   (б) `qty > m · медиана месячных отгрузок SKU`. `k` (10σ…3σ) и `m` (1.0…0.25) задаются
   `outlier_sensitivity`. Условие (б) важно: у ходовых позиций регулярный опт — норма, его исключать нельзя.
   Для редких SKU (< 8 строк): строка исключается, если даёт > 50% всех отгрузок товара и ≥ 50 ед.
   Клиентов в данных нет → детекция по объёму строки (ТЗ §2.3).
2. **Компенсация stockout.** По остаткам на начало месяца и следующего: доступность месяца 1 / 0.5 / 0.
   Спрос месяцев с дефицитом досчитывается до среднего спроса месяцев с полным наличием:
   `corrected = demand + (1 − a)·max(ref − demand, 0)`.
3. **Базовый спрос** — среднее скорректированного спроса за 12 последних полных месяцев.
4. **Сезонность.** Индекс поставщика — по выручке компании («Сезонность»), методом отношения к центрированному
   12-мес. скользящему среднему (убирает тренд). Индекс SKU — по последним 12 месяцам с удалением линейного
   тренда, «стянутый» к индексу поставщика с весом по числу активных месяцев и объёму (шумоустойчиво).
5. **Тренд** — год к году за последние 6 месяцев, стянутый к 1 для малых объёмов и экстраполированный
   от середины 12-мес. базы до середины окна покрытия; ограничен [0.5; 2].
6. **Потребность** = прогноз на (срок поставки + горизонт) + страховой запас (дни буфера × множитель категории)
   − свободный остаток − товар в пути → округление вверх по MOQ и кратности.
7. **Срочность** — по дню, когда остаток (с учётом дат поступления товара в пути) уйдёт в ноль:
   `high` — раньше, чем придёт заказ, сделанный сегодня; `medium` — в пределах срока поставки + буфер; иначе `low`.

Каждый шаг сохраняет факторы в `sku_forecasts.explanation` → `narrative` собирается из них (`engine/explain.py`).

## Что выяснилось по данным (важно для команды)

- **Транзакции «Динамика продаж» начинаются фактически с 01.2025** (до этого — только единичные возвраты),
  а не с 07.2023, как указано в ARCHITECTURE.md. История для расчёта — 20 месяцев; движок это учитывает.
- **Номера документов сбрасываются каждый год** — документ уникален только в паре «номер + год».
- **SE: транзакции ≈ в 2 раза больше отчёта «Ежемесячные продажи»** (для IEK совпадают на 93–100%).
  Разница — в основном монтажные коробки (030200192_, 030200201_, 030300014_…). Ручной расчёт менеджера
  (`Кэф. Роста`, `Кэф. Сез-ти`) построен на помесячном отчёте, а не на транзакциях → эталон с нашим расчётом
  напрямую не сопоставим. **Вопрос к партнёру:** что попадает в «Динамику продаж» и не попадает в отчёт.
- Формулы эталона (восстановлены из xlsx): `Кэф. Роста = Σ(июн–авг 2026)/Σ(июн–авг 2025) − 1`,
  `Кэф. Сез-ти = Σ(сен–ноя 2025)/Σ(июн–авг 2025) − 1`,
  `Запас = (свободный + ТЗ + розница + витрина + заказ + в пути) / среднемесячные продажи` (в месяцах);
  колонка `Заказ` в файле пустая. РЦ Рыскулова в «Запас» не входит — так же сделано у нас.
- **IEK: нет снимка текущих остатков** — остаток оценивается как «остаток на 01.09 − отгрузки с 01.09»
  (без учёта поступлений в сентябре). В обосновании это помечено.
- IEK «Мин. разр. к отгр.» трактуется как минимальная партия (кратность 1) — нужно подтвердить.
- Категории (1, 2, 3, 5, 7) есть только у SE-позиций из файла «Товар в пути»; остальные — «Без категории».
- Сроки поставки по умолчанию: IEK 45 дн., SE 30 дн. — настраиваются через `PUT /api/suppliers/{id}`.
