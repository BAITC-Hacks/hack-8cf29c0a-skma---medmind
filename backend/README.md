# Backend — расчёт заказов поставщикам

Python 3.12 · FastAPI · SQLAlchemy + SQLite · pandas/numpy.
API реализует контракт из [`FRONTEND_TZ.md` §0.3–0.4](../FRONTEND_TZ.md).

База проекта — SQLite: `DATABASE_URL=sqlite:///./var/hackalem.db`.
При запуске из `backend/` данные хранятся в `backend/var/hackalem.db`.
Каталог и таблицы создаются при инициализации; отдельный сервер БД не требуется.
Для файловой базы включён режим WAL.

## Загрузка и ручное управление входными данными

Добавлены CRUD `/api/input-data/*`, импорт CSV/XLSX с сопоставлением колонок и
API загрузки исходных ZIP-комплектов IEK/Systeme Electric. Поддерживаются preview,
атомарная запись, повторный импорт по внешним идентификаторам и аудит изменений.
Схемы видны в Swagger. Форматы, примеры и правила замены данных — в [INPUT_DATA.md](INPUT_DATA.md).

## Запуск

```bash
# один раз: uv (https://docs.astral.sh/uv/) сам поставит Python 3.12 и зависимости
cd backend
cp .env.example .env          # DATA_DIR — папка с xlsx партнёра (подпапки IEK и Systeme electric)
uv sync

uv run hackalem ingest        # xlsx → БД (~40 с), перезаливает данные поставщиков
uv run hackalem calc          # расчёт рекомендаций (~3 с)
uv run hackalem serve --reload  # API на http://127.0.0.1:8000, Swagger: /docs

uv run pytest                 # тесты (синтетические данные, реальные файлы не нужны)
uv run ruff check src tests
```

Фронт: `VITE_USE_MOCK=false`, `VITE_API_BASE_URL=http://127.0.0.1:8000/api` (CORS для `localhost:5173` открыт).

## Тестовые данные (сидер)

Из `backend/`:

```bash
uv run hackalem seed
```

Из корня репозитория: `uv run --directory backend hackalem seed`.
`uv run` устанавливает зависимости, CLI создаёт таблицы и атомарно загружает комплект из
`src/app/seed_data/` (около 3,3 МБ). Внешние Excel-файлы, `DATA_DIR` и API-ключи не нужны.
Целевая база задаётся `DATABASE_URL` в окружении или `backend/.env`; по умолчанию — `var/hackalem.db`.

Снимок содержит все таблицы текущей базы, **кроме `sku_forecasts`**: поставщиков, категории,
товары, историю продаж, месячные и текущие остатки, товары в пути, MOQ/кратность, сезонность,
эталонные показатели, настройки, заказы, связанную историю расчётов, аудит и данные ассистента.
Точные количества строк и SHA-256 файлов записаны в `src/app/seed_data/manifest.json`.
Прогнозы и обоснования не загружаются и не вычисляются. Для их получения отдельно запустите
`uv run hackalem calc`. Сохранённые заказы доступны через API сразу после сидирования.

- Повторный запуск возвращает `already_seeded`: дубли не создаются, изменения пользователя сохраняются.
- Заполненная база без отметки этого сидера не изменяется; используйте отдельный `DATABASE_URL`.
- Если API уже создал настройки расчёта, сидер сохраняет их значения.
- При ошибке файла, контрольной суммы или записи откатывается весь импорт.
- Успешная загрузка отмечается дополнительной записью `seed` в `audit_log`.

Сидер работает с серверными данными. `VITE_USE_MOCK=false` подключает заказы к API;
страницы товаров, истории продаж и дашборда пока используют собственные локальные демоданные.

Для обновления комплекта из локальной базы (источник открывается только для чтения):

```bash
uv run python scripts/export_seed.py var/hackalem.db
```

Экспорт не включает `sku_forecasts` и служебную отметку установки сидера; остальные данные
сохраняются без изменения идентификаторов и дат. Проверьте содержимое перед коммитом:
в том числе историю ассистента и вложения, если они присутствуют в исходной базе.
Идентификатор комплекта зависит от содержимого: изменённый снимок следует устанавливать в новую пустую базу.

## Ручное управление заказами

В текущей модели заказ — одна товарная позиция (`OrderRecommendation`) в расчёте,
а не отдельный документ с несколькими строками. Создание принимает код существующего
товара; поставщик, категория и единица измерения берутся из каталога. Один SKU в одном
расчёте не дублируется (409). Если `run_id` отсутствует, создаётся завершённый набор
с `params.source=manual` без расчёта прогноза. Его можно выбирать как обычный расчёт;
прогнозной аналитики у него нет. Для следующих позиций передавайте возвращённый `run_id`.

PUT требует `recommended_qty`, `urgency` и `short_reason`; PATCH принимает хотя бы
одно изменяемое поле. Количество конечное, больше 0 и до 1 000 000 включительно;
допускается дробное. Обоснование — 1–2000 символов, комментарий — до 500.
Товар и расчёт позиции неизменяемы. Любое фактическое изменение сбрасывает согласование
в `pending`, очищает `approved_qty` и дату решения. Запрос без изменения значений
сохраняет статус. Утверждение и отклонение доступны отдельными POST-запросами.

Изменения разрешены для завершённых расчётов и блокируются на время выполняющегося
пересчёта (409). Отсутствующая позиция возвращает 404, невалидные данные — 422.
Создание, изменение, удаление и решения записываются в `audit_log`. Удаление убирает
позицию из списка и последующего экспорта; ранее выгруженные файлы остаются.
`sku_forecasts` не меняется: после редактирования интерфейс показывает исходный
прогноз отдельно от текущего количества. Новый пересчёт может снова рекомендовать
удалённый товар. Изменение схемы SQLite для этого CRUD не требуется.

## Методология расчёта (`engine/core.py`)

Всё считается по каждому SKU, дата расчёта — самая свежая дата в данных (последняя отгрузка / снимок остатков).

1. **Исключение разовых/оптовых заказов.** Для строк отгрузок SKU считаются медиана и MAD. Строка исключается,
   если одновременно: (а) `qty > max(median + k·σ̂, p95)`, σ̂ = max(1.4826·MAD, 0.5·median, 1);
   (б) `qty > m · медиана месячных отгрузок SKU`. `k` (10σ…3σ) и `m` (1.0…0.25) задаются
   `outlier_sensitivity`. Условие (б) важно: у ходовых позиций регулярный опт — норма, его исключать нельзя.
   Для редких SKU (< 8 строк): строка исключается, если даёт > 50% всех отгрузок товара и ≥ 50 ед.
   Клиентов в данных нет → детекция по объёму строки (ТЗ §2.3).
2. **Компенсация stockout.** По остаткам на начало месяца и следующего: доступность месяца 1 / 0.5 / 0.
   Спрос месяцев с дефицитом досчитывается до среднего спроса месяцев с полным наличием:
   `corrected = demand + (1 − a)·max(ref − demand, 0)`.
3. **Базовый спрос** — среднее скорректированного спроса за 12 последних полных месяцев.
4. **Сезонность.** Индекс поставщика — по выручке компании («Сезонность»), методом отношения к центрированному
   12-мес. скользящему среднему (убирает тренд). Индекс SKU — по последним 12 месяцам с удалением линейного
   тренда, «стянутый» к индексу поставщика с весом по числу активных месяцев и объёму (шумоустойчиво).
5. **Тренд** — год к году за последние 6 месяцев, стянутый к 1 для малых объёмов и экстраполированный
   от середины 12-мес. базы до середины окна покрытия; ограничен [0.5; 2].
6. **Потребность** = прогноз на (срок поставки + горизонт) + страховой запас (дни буфера × множитель категории)
   − свободный остаток − товар в пути → округление вверх по MOQ и кратности.
7. **Срочность** — по дню, когда остаток (с учётом дат поступления товара в пути) уйдёт в ноль:
   `high` — раньше, чем придёт заказ, сделанный сегодня; `medium` — в пределах срока поставки + буфер; иначе `low`.

Каждый шаг сохраняет факторы в `sku_forecasts.explanation` → `narrative` собирается из них (`engine/explain.py`).

## «Ленивый режим» — ИИ-ассистент (`app/assistant/`)

Менеджер спрашивает обычным языком («что срочно заказать у IEK?», «покажи динамику по коробкам 65х45»,
«вот выгрузка — дай прогноз на квартал»), ассистент сам находит данные, объясняет выводы и строит кривые.

Frontend всегда вызывает этот API, включая `VITE_USE_MOCK=true`: деморежим заказов не подменяет ответы
ассистента. Настройки OpenAI загружаются из `backend/.env` независимо от рабочей папки; после изменения
ключа или моделей перезапустите backend. `GET /api/assistant/status` показывает наличие ключа и настроенные
модели, но не проверяет квоту и доступ к ним. Ошибки OpenAI возвращаются без ключа и сырого текста SDK;
незавершённый или пустой ответ не сохраняется как успешный ход диалога.

Инструменты возвращают `order_url` рядом с товарами, для которых существует рекомендация. Ассистент
вставляет эти ссылки в ответ: они открывают карточку заказа поверх чата с актуальным статусом,
количеством и ручным утверждением. Переход по ссылке ничего не утверждает; сохранение выполняется
только кнопкой «Утвердить» через API рекомендаций. Товары только из файла без заказа ссылок не получают.

- **Модели** (OpenAI Responses API, задаются в `.env`), режим выбирается в каждом сообщении (`mode`):
  `fast` → `gpt-6-luna` (быстрые справки), `standard` → `gpt-6-sol` (по умолчанию: инструменты, файлы, графики),
  `deep` → `gpt-6-astra` (сложные сравнения и разборы). Ключ можно добавить, заменить или удалить
  в «Настройки → ИИ-ассистент». Он хранится в серверной БД, применяется со следующего запроса
  без перезапуска и не возвращается клиенту. Ключ общий для всех пользователей приложения.
  Сохранённый ключ имеет приоритет над `OPENAI_API_KEY`; после удаления используется ключ
  из окружения. Если оба отсутствуют, отправка сообщений отвечает 503.
- **Модель не видит БД напрямую** — только 10 инструментов (`assistant/tools.py`): обзор расчёта, поиск SKU,
  разложение расчёта по товару, список рекомендаций, динамика, сезонность, анализ/прогноз файла, произвольная
  кривая. Все цифры в ответах — из них. Ничего не утверждает и не отправляет.
- **Файлы** (CSV/XLSX ≤ 20 МБ) разбираются на сервере: «Дата | Код | Количество» (как «Динамика продаж») или
  «Товар | янв. 2025 | …». Прогноз — та же методика, что в движке (`engine/timeseries.py`), с исключением разовых
  отгрузок и отбрасыванием неполного последнего месяца. В OpenAI уходят только агрегаты, не строки файла.
- **Приватность:** `store=false`, история диалогов хранится в нашей БД. Данных о клиентах в запросах нет.
- **Графики** приходят в `assistant_message.charts` как спецификация для Recharts (цвета — токены фронта по `kind`):

```json
{"id": "…", "type": "line", "title": "Динамика спроса: IEK", "subtitle": "…", "x_key": "period", "y_label": "шт",
 "series": [{"key": "actual", "name": "Факт", "kind": "actual"}, {"key": "forecast", "name": "Прогноз", "kind": "forecast"}],
 "data": [{"period": "2026-07", "actual": 224019, "forecast": null}, {"period": "2026-08", "actual": 198656, "forecast": 198656},
          {"period": "2026-09", "actual": null, "forecast": 181200}]}
```
`kind`: `actual` — сплошная линия, `forecast` — пунктир (стыкуется с последней точкой факта), `series` — прочие ряды.

## Что выяснилось по данным (важно для команды)

- **Транзакции «Динамика продаж» начинаются фактически с 01.2025** (до этого — только единичные возвраты),
  а не с 07.2023, как указано в ARCHITECTURE.md. История для расчёта — 20 месяцев; движок это учитывает.
- **Номера документов сбрасываются каждый год** — документ уникален только в паре «номер + год».
- **SE: транзакции ≈ в 2 раза больше отчёта «Ежемесячные продажи»** (для IEK совпадают на 93–100%).
  Разница — в основном монтажные коробки (030200192_, 030200201_, 030300014_…). Ручной расчёт менеджера
  (`Кэф. Роста`, `Кэф. Сез-ти`) построен на помесячном отчёте, а не на транзакциях → эталон с нашим расчётом
  напрямую не сопоставим. **Вопрос к партнёру:** что попадает в «Динамику продаж» и не попадает в отчёт.
- Формулы эталона (восстановлены из xlsx): `Кэф. Роста = Σ(июн–авг 2026)/Σ(июн–авг 2025) − 1`,
  `Кэф. Сез-ти = Σ(сен–ноя 2025)/Σ(июн–авг 2025) − 1`,
  `Запас = (свободный + ТЗ + розница + витрина + заказ + в пути) / среднемесячные продажи` (в месяцах);
  колонка `Заказ` в файле пустая. РЦ Рыскулова в «Запас» не входит — так же сделано у нас.
- **IEK: нет снимка текущих остатков** — остаток оценивается как «остаток на 01.09 − отгрузки с 01.09»
  (без учёта поступлений в сентябре). В обосновании это помечено.
- IEK «Мин. разр. к отгр.» трактуется как минимальная партия (кратность 1) — нужно подтвердить.
- Категории (1, 2, 3, 5, 7) есть только у SE-позиций из файла «Товар в пути»; остальные — «Без категории».
- Сроки поставки по умолчанию: IEK 45 дн., SE 30 дн. — настраиваются через `PUT /api/suppliers/{id}`.
