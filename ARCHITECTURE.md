# HackAlem AI: Автоматизация формирования заказов поставщикам
## Анализ ТЗ, данных и базовая архитектура WEBAPP

Партнёр: ТОО «Электрокомплект» (ekt.kz). Кейс: автоматический расчёт заказов поставщикам для пополнения склада на основе истории продаж, остатков, товаров в пути, сезонности и MOQ.

---

## 1. Анализ технического задания

### 1.1 Проблема
Менеджер закупок вручную считает пополнение склада в Excel — процесс трудоёмкий, выполняется редко и не в реальном времени. Крупные разовые/оптовые заказы искажают расчёт регулярного спроса → избыточные остатки по одним товарам и дефицит по другим.

### 1.2 Пользователь
Менеджер отдела закупок: выбирает склад/категорию → получает список рекомендованных заказов с обоснованием → проверяет/корректирует → **утверждает вручную** (автоотправка запрещена).

### 1.3 Must-have требования
1. **Базовый расчёт потребности** — одновременно по 5 источникам: история продаж, текущие остатки, товары в пути, категория товара, прогноз роста спроса.
2. **Сезонность и тренд роста** — прогноз распознаёт сезонные паттерны и устойчивый рост, а не просто усредняет историю.
3. **Компенсация stockout** — периоды отсутствия товара на складе увеличивают расчётную потребность.
4. **Исключение разовых/оптовых заказов** — выбросы не должны искажать расчёт регулярного спроса.
5. **Структурированный вывод** — список группируется по поставщикам, каждая позиция содержит текстовое обоснование количества.

### 1.4 Nice-to-have
- Приоритизация по риску дефицита
- Учёт MOQ/кратности и условий поставщика
- Визуализация трендов спроса
- Экспорт/отправка заказа поставщику после одобрения

### 1.5 Ограничения (constraints)
- Нет автоотправки заказа без подтверждения человека
- Обязательная анонимизация данных о клиентах
- **Explainability** — каждая рекомендация обоснована прозрачно
- Устойчивость к аномалиям/выбросам во входных данных
- Совместимость выходных форматов с 1С

### 1.6 Артефакты сдачи
Git-репозиторий + README (методология расчёта, алгоритм исключения выбросов, инструкция по запуску).

## 2. Анализ реальных данных (IEK + Systeme Electric)

Изучено 12 Excel-файлов — по 6 на каждого поставщика. Ниже — фактическая структура и расхождения с исходным ТЗ.

### 2.1 Структура файлов по типу

| Тип файла | Поля | Особенности |
|---|---|---|
| **Динамика продаж** (транзакции) | Дата, Номер, Документ, Код (SKU), Номенклатура, Ед., Склад, Количество (знак «-» = отгрузка) | IEK: 171 605 строк (07.2023–09.2026); SE: 77 314 строк (01.2023–09.2026). Склад везде один — «Алматы». |
| **Ежемесячные остатки** | Номенклатура, Код, [нач. остаток по 35 месяцам: янв.2024–сент.2026] | Матрица SKU × месяц |
| **Ежемесячные продажи (кол-во)** | тот же помесячный формат | Агрегат транзакций по месяцам — можно использовать для кросс-валидации ETL |
| **MOQ** | IEK: `Код 1с`, `Артикул поставщика`, `Наименование`, **`Мин. разр. к отгр.`**; SE: `Номенклатура`, `Код`, `Артикул`, **`Кратность`** | Разные единицы ограничения: у IEK — минимальная партия отгрузки, у SE — кратность (лот) |
| **Товар в пути** | IEK: отдельная колонка на каждый номер поставки (`РФ УТ-7583 от 31.08.2026 (поступление до 10.10.2026)` и т.д.); SE: агрегированная колонка `СЭ в пути 24.09` | Структурно несовместимы между поставщиками |
| **Сезонность** | год × 12 месяцев, сумма в KZT | Это **агрегат выручки компании**, НЕ по SKU |

### 2.2 Ключевая находка: эталонный расчёт уже существует

Файл `Товар в пути_SystemElectric` — фактически ручной аналог того, что должна делать система. В нём уже посчитаны:

- `Кэф. Роста`, `Кэф. Сез-ти` — коэффициенты роста и сезонности по SKU
- Разбивка остатка по локациям: `Витрина`, `Остаток ТЗ`, `РЦ ЕКТ Рыскулова`, `Розничный склад`
- `Зарезервировано` → `Свободный остаток`
- `Запас` (буфер) и **`Заказ`** (итоговое рекомендованное количество)

Это ground truth для валидации алгоритма и реверс-инжиниринга бизнес-формулы буфера/заказа.

### 2.3 Расхождения с исходным ТЗ

1. **Нет ID клиента.** В транзакциях есть только номер документа, обезличенного ID клиента нет. Требование «исключение разовых заказов» переформулировано: детекция выбросов **по объёму строки документа относительно исторического распределения продаж SKU**, а не кластеризацией по клиентам.
2. **Разные форматы у поставщиков.** IEK и SE структурно несовместимы (goods-in-transit, MOQ) → нужен слой supplier-specific ETL-адаптеров, а не единый парсер.
3. **Склад один — «Алматы».** Многоскладовость из ТЗ на практике — это суб-локации внутри одного склада (витрина / склад ТЗ / РЦ / розница), а не разные города.
4. **Категория — числовой код** (1, 2, 3, 5, 7 у SE) без расшифровки в файлах. Открытый вопрос к партнёру: нужен справочник категорий.
5. **Сезонность в файлах — агрегат по компании**, не по SKU. Per-SKU сезонность система считает сама, ориентируясь на `Кэф. Сез-ти` как валидационный пример.
6. Глубина истории — ~3 года (07.2023–09.2026), это лучше, чем предполагалось в ТЗ — достаточно для сезонности и тренда.

### 2.4 Обновлённые Must-have (после анализа данных)

1. Расчёт на уровне `Код 1С` (первичный ключ) + `Артикул поставщика` как вторичный идентификатор.
2. ETL-адаптеры per-supplier (IEK / Systeme Electric на старте, архитектура расширяемая).
3. Детекция выбросов — на уровне строки документа (объём/SKU/дата), без привязки к клиенту.
4. Остатки — на уровне суб-локации склада, с учётом `Зарезервировано` → `Свободный остаток`.
5. MOQ/кратность нормализуются в единый концепт: `min_order_qty` + `order_multiple`.
6. Расчёт валидируется против эталонных колонок (`Кэф. Роста`, `Кэф. Сез-ти`, `Заказ`) из файла SE как тестовый набор.

### 3.1 Модель данных (ключевые таблицы)

- `sku_master` (код_1с PK, артикул_поставщика, наименование, категория_код, поставщик_id, вес)
- `sales_transactions` (дата, документ_номер, sku_код, склад/локация, количество, знак)
- `stock_snapshots` (sku_код, локация, месяц, остаток, зарезервировано)
- `goods_in_transit` (sku_код, поставщик, номер_заказа, дата_ожид_поступления, количество)
- `supplier_rules` (поставщик_id, sku_код, min_order_qty, order_multiple, lead_time_days)
- `calc_runs` (run_id, дата, параметры горизонта/буфера)
- `order_recommendations` (run_id, sku_код, поставщик, рек_количество, обоснование_json, срочность)

### 3.2 Расчётный пайплайн

Реализует все 5 must-have требований последовательно, сохраняя промежуточные факторы (`base_demand`, `seasonality_factor`, `growth_factor`, `stockout_compensation`, `bulk_outlier_flag`) в JSON — основа для explainability и валидации против эталона `Заказ`/`Кэф.` из файла System Electric.

### 3.3 Стек (предложение)

- **Backend/расчёт**: Python + FastAPI + pandas/numpy/statsmodels
- **БД**: SQLite через SQLAlchemy, файловая база `backend/var/hackalem.db`, режим WAL
- **Планировщик**: Celery / APScheduler для периодических расчётов
- **Frontend**: React + TypeScript
- **Экспорт**: openpyxl (Excel/CSV совместимые с 1С), PDF-рендер
